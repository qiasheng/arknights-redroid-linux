# 07 · 踩坑记录：走过的弯路

这篇不是教程，是复盘。记录「当时以为是什么、为什么错、最后怎么定位」。下次遇到新问题，可以先看看有没有类似的思维陷阱。

---

## 1. 「下载慢 / 断流」→ 以为是 DNS

**当时的判断**：游戏能登录、能校验，但下载资源时速度掉 0，第一反应是 DNS 被污染或解析慢。

**实际测试**：

| DNS | 延迟 |
|---|---|
| 8.8.8.8 | 1.4–1.7 ms |
| 223.5.5.5 | 1.4–1.7 ms |
| 119.29.29.29 | 1.4–1.7 ms |
| 192.168.31.1 | 1.4–1.7 ms |

容器实际用 `8.8.8.8`，连续 64 次查询 0 错误。还试过：

```bash
adb shell cmd netd resolver setnetdns 100 "" 223.5.5.5
```

命令返回成功，但实际解析路径没变，**不生效**。

**真相**：PPPoE 链路 MTU 1492，容器 1500，大包被丢，PMTUD 又收不到 ICMP 反馈。小包能过 → 表现为「能登录、不能下载」。

**教训**：DNS 问题表现为「解析失败 / 解析慢」，不是「大文件传到一半停住」。后者优先查 MTU。

---

## 2. 「进游戏被踢」→ 以为是内存不足

**当时的判断**：进主界面后几十秒进程消失，很像资源加载爆内存被 OOM。

**实际检查**：

```bash
adb shell dmesg | grep -i oom        # 空
adb shell logcat -b events | grep am_kill  # 空
adb shell cat /proc/meminfo          # 内存充足
```

OOM 会留下内核日志和 `am_kill`，这里都没有。进程是 `exited cleanly (0)` 或 `signal 9`，但**没有 tombstone**。这不是崩溃，是主动退出。

**教训**：先分清「崩溃」「被系统杀」「主动退出」三类。没有 tombstone + 没有 OOM 日志 + zygote 说 clean exit = 程序自己走的。

---

## 3. 「进游戏被踢」→ 以为是翻译层不兼容

**当时的判断**：ARM 翻译层跑 Unity 游戏本来就不稳，崩铁也遇到过 `Undefined instruction`，所以方舟被踢大概率也是翻译层。

**实际**：翻译层确实有问题，但表现是**启动即 SIGABRT**（`libvulkan.so` 的 `android_convertGralloc0To1Usage`），修完这个之后，游戏能进主界面，然后才被 TenProtect 杀掉。这是两个独立问题，被同一个「游戏起不来」的表象串在一起。

**教训**：一个问题修完后「表现变了」，要重新定位，不要把旧结论套到新现象上。

---

## 4. 「启动崩溃」→ 只换翻译层，不换 guest 库

**当时的判断**：libndk v0.2.2 太旧，只把 `libndk_translation*.so` 换成 v0.2.3 就行，guest 库保持 Android 11 原版。

**实际**：仍然 SIGABRT。最后采用「整套 v0.2.3」——翻译层 + 60 个 arm64 guest 库 + 60 个 arm guest 库，并且禁用 guest `libvulkan.so`。

**教训**：翻译层和 guest 库是配套的，版本要一起换。只换一半容易出奇怪问题。

---

## 5. 「启动崩溃」→ 以为禁用 libvulkan 会黑屏

**当时的担心**：方舟是 Unity 游戏，禁用 Vulkan 会不会直接黑屏？

**实际**：方舟本来就用 GLES。禁掉 guest `libvulkan.so` 后，Unity 检测不到 Vulkan，自动回落 GLES，渲染完全正常。真正需要 Vulkan 的游戏（比如某些新游）才不能这么干。

**教训**：先确认游戏实际用的渲染后端，再决定要不要保留 Vulkan。

---

## 6. 「卡在加载页」→ 以为是 bug / 资源没下完

**当时**：加载页停住，logcat 没有任何错误，等 3 分钟、10 分钟都不动。以为是热更没完成、翻译层卡死、资源缺失。

**真相**：这个页面底部有一个很暗的金色菱形，**必须点**。它不是「加载中」，是「点击开始」。

**怎么发现的**：截图放大底部，看到有个菱形；用 `input tap` 点了一下，立刻进登录页。

**教训**：Android 游戏里「看起来像加载页」的界面，可能是一个等待点击的页面。先截图看有没有按钮，再怀疑技术问题。

---

## 7. 「点不动」→ 以为是触摸坐标不对

**当时**：按 1280×720 的坐标点，没反应；换成 1920×1080 的坐标，还是没反应。

**实际**：`wm size` 设置了 override 1920×1080，但 `input tap` 用的是**逻辑坐标**，应该按 override 后的分辨率算。另外，屏幕当时是休眠的，点击被丢弃。

**教训**：

```bash
adb shell wm size          # 看 Override size
adb shell dumpsys power | grep mWakefulness
```

先确认分辨率和屏幕状态，再调坐标。

---

## 8. 「MAA 连不上」→ 以为是端口 / 防火墙

**当时**：MAA 里填了 `127.0.0.1:5556`，连不上；`adb devices` 在宿主是好的。

**实际**：Wine 里的 `adb.exe` 需要的是 Windows 路径，`AdbPath` 填了 Linux 的 `/usr/bin/adb`，MAA 启动失败。改成 `Z:\home\<you>\Games\MAA\platform-tools\adb.exe` 后正常。

另外，MAA 同时看到 5555 和 5556，自动选了 5555（崩铁）。必须在地址里写死 5556。

**教训**：Wine 程序的路径是 Windows 语义，`Z:` 才是 Linux 根目录。

---

## 9. 「MAA 启动失败」→ 以为是 Wine 不行

**当时的判断**：MAA 是 .NET/WPF，Wine 跑不起来很正常，准备放弃。

**实际**：报错是 `MaaCore.dll 加载失败`，原因是缺 VC++ 运行库 + 解压不完整。装 `vcrun2022`、重新完整解压后正常。日志里明确写了 `Running under Wine 11.0`，Wine 本身没问题。

**教训**：先读日志里的具体错误，不要用「Wine 兼容性差」这种笼统结论放弃。

---

## 10. `pkill -f lutris` 把自己杀了

**操作**：

```bash
pkill -f lutris
```

**结果**：终端直接断开，命令没执行完。

**原因**：`pkill -f` 匹配整条命令行，而执行这条命令的 shell 命令行里就包含 `lutris`，于是它把自己（以及父 shell）杀了。

**正确**：

```bash
pkill -x lutris     # 只匹配进程名
pgrep -a lutris     # 先看
kill <pid>
```

**教训**：任何 `pkill -f <pattern>` 都要先想「我自己的命令行里有没有这个 pattern」。

---

## 11. 装 `tcpdump` 破坏依赖

**操作**：

```bash
sudo pacman -S tcpdump
```

**结果**：触发 `libcrypto.so=3-64` 依赖冲突，牵连 OpenSSL，podman / git / curl 都受影响。

**处理**：卸载 tcpdump，回滚 OpenSSL，`pacman -Syu` 修复。

**教训**：Arch 上为了抓一次包装工具，风险比收益大。用 `ss`、`nft`、`ip -s link` 足够定位大部分网络问题；真需要抓包，用 `podman run --net=host nicolaka/netshoot` 之类的临时容器。

---

## 12. `grep "0% packet loss"` 误判

**操作**：

```bash
ping -c 3 8.8.8.8 | grep "0% packet loss"
```

**结果**：100% 丢包也匹配，因为 `100% packet loss` 里包含 `0% packet loss`。

**正确**：

```bash
ping -c 3 8.8.8.8 | grep -w "0% packet loss"
# 或者直接看退出码
ping -c 3 8.8.8.8 >/dev/null && echo OK
```

**教训**：文本匹配数字时要加词边界，或者用结构化输出。

---

## 13. `adb root` 把 adbd 弄没了

**操作**：

```bash
adb root
```

**结果**：设备从 `adb devices` 消失，重连也连不上。

**原因**：redroid 的 adbd 在 root 重启时可能起不来。

**处理**：

```bash
sudo podman restart redroid-arknights
adb connect 127.0.0.1:5556
```

**教训**：redroid 里本来就能 `su 0`，不需要 `adb root`。需要 root 时用：

```bash
adb shell 'su 0 <command>'
```

---

## 14. 用 `setprop` 改 fingerprint

**操作**：

```bash
adb shell setprop ro.build.fingerprint "xxx"
```

**结果**：失败 / 没变化。

**原因**：`ro.*` 是只读属性，只能在启动时由 prop 文件设置，运行时不能改。

**正确**：改 `/system/build.prop`，然后重启容器（见 02）。

**教训**：Android 属性分 `ro.*`（只读，启动时定）和 `persist.*`（可写，存 `/data`）。改之前先确认类型。

---

## 15. 以为 `podman restart` 会保留一切

**操作**：改完 `/system`，`podman restart`，验证 OK。过几天 `podman rm` 重建容器，所有修改消失。

**原因**：`/system` 的修改在容器可写层，`rm` 会销毁可写层；`/data` 是 bind mount，所以数据还在。

**正确**：

- 重建后重跑 01 第 6 节 + 02；
- 或者 `podman commit` 保存镜像；
- 或者把修复写进启动脚本（本仓库的 `scripts/`）。

**教训**：区分「容器可写层」「bind mount」「镜像」三层，别假设修改永久。

---

## 16. 想用 Waydroid 备份，最后没选

**考虑过**：Waydroid 也是 Android 容器，ADB 也能连，MAA 理论上也能用。

**没选的原因**：

- Waydroid 需要 Wayland 会话，无头 / 远程场景麻烦；
- binder / 内核模块依赖更重；
- 已经有一套能跑的 redroid（崩铁），复用同一套镜像和翻译层更省事；
- redroid 的 `/system` 可写，改 fingerprint / 翻译层很方便。

**结论**：Waydroid 不是不能做，而是这个场景下 redroid 更顺手。如果哪天 redroid 跑不动，Waydroid 可以作为备选，思路（fingerprint、libndk、MTU、坐标）是一样的。

---

## 17. 试过官方 Windows PC 客户端

**结论**：不行。MAA 只支持 Android 客户端（通过 ADB）。官方 PC 客户端是另一套架构，MAA 无法接管。

**教训**：需求里「必须跑在 MAA 可用的 ADB 环境」这一条，直接排除了 PC 客户端。

## 18. 一些「看起来是问题，其实不是」的现象

| 现象 | 真相 |
|---|---|
| 加载页不动 | 要点金色菱形 |
| 游戏没声音 | redroid 默认无音频，预期行为 |
| MAA 提示 419 个文件缺失 | 文件名被按 CP866 解码，文件本身都在（见第 21 节） |
| MAA 警告 GPU 驱动信息读不到 | Wine 读不到 AMD 驱动版本，OCR 仍正常 |
| `MaaWineBridge NotAvailable` | Linux 集成桥不可用，不影响 ADB 控制 |
| `settings put global private_dns_mode off` 重启后还在 | 它存在 `/data`，容器重启保留；`rm` 才丢 |
| `podman0` MTU 重启后有时还是 1492 | 网桥可能复用，但容器 eth0 一定回到 1500，仍要跑脚本 |
| 容器里 `getprop` 有很多属性是空 | 镜像精简，正常 |

## 19. 如果重来一次，我会按这个顺序

1. 先确认内核 binder / ashmem，再拉镜像；
2. 容器起来先设分辨率、关私有 DNS、关门户检测；
3. 装 APK 时**立刻**加 `--abi arm64-v8a`，装完验证 `primaryCpuAbi`；
4. 换整套 libndk v0.2.3，**同时**禁用 guest libvulkan；
5. 第一件事就检查 fingerprint 长度，不要等游戏跑起来才查；
6. 先修 MTU，再让游戏下载资源；
7. 手动走一遍启动流程，截图记下金色菱形和开始唤醒的坐标；
8. 最后再配 MAA，避免把「游戏问题」误判成「MAA 问题」；
9. 所有修改写成脚本，`podman rm` 后能一键恢复；
10. 每修一个现象，重新做一次「现象 → 证据 → 结论」，不要沿用上一个问题的结论。

## 20. 最后：排查方法比结论更重要

这次真正解决问题的不是「某个神奇的配置」，而是几个习惯：

- **先分类**：崩溃 / 被系统杀 / 主动退出，三类证据完全不同；
- **看证据**：`dmesg`、`logcat -b events`、`tombstones`、`am_proc_died`、gdb/jdb；
- **别猜**：DNS 慢就测延迟，MTU 不对就 `ping -M do` 二分，属性超长就看 `libc` 日志；
- **改一个变量**：一次只改一处，否则不知道是哪一处生效；
- **记录**：每个「试过但没用」的方向都写下来，避免下次重复。

这套环境里的三个核心问题（fingerprint、libvulkan、MTU）都不是「配置项写错」，而是**运行时行为与预期不符**。理解它们为什么发生，比记住命令更有用。

## 21. MAA 的 419 个「缺失文件」其实是文件名乱码

**当时的疑问**：Lutris 的工作目录明明设成了 `~/Games/MAA`，MAA 也在这个目录里跑，怎么会缺文件？

**先确认工作目录没问题**。MAA 日志里写得很清楚：

```
User Dir Z:\home\<you>\Games\MAA\
LoadResource Enter
Load resource: X:\Games\MAA\resource
AsstLoadResource ret: true
```

`Z:` 和 `X:` 都指向宿主目录，资源也确实从解压目录加载了。所以不是「工作目录设错」。

**真正的原因**：MAA 的完整性检查是拿 `filelist.txt` 里的**文件名**逐个比对，而不是只看目录在不在。解压目录里有 419 个名字对不上：

```
filelist 期望:  DependencySetup_依赖库安装.bat
磁盘实际:      DependencySetup_ф╛Эш╡Цх║УхоЙшгЕ.bat

filelist 期望:  Res/Backgrounds/Wallpapers/牛牛表情包1/01.喜报.jpg
磁盘实际:      Res/Backgrounds/Wallpapers/чЙЫчЙЫшбицГЕхМЕ1/01.хЦЬцКе.jpg

filelist 期望:  resource/copilot/old/施佩尔山脚_Spier_Foothills/...
磁盘实际:      resource/copilot/old/цЦ╜ф╜йх░Фх▒▒шДЪ_Spier_Foothills/...
```

文件内容一个不少，只是**名字被错误解码**了。

**怎么确认是哪种编码**：

```bash
python3 - <<'PY'
s = '牛牛表情包1'
print(s.encode('utf-8').decode('cp866'))   # чЙЫчЙЫшбицГЕхМЕ1
print('чЙЫчЙЫшбицГЕхМЕ1'.encode('cp866').decode('utf-8'))  # 牛牛表情包1
PY
```

磁盘上的乱码正好是「UTF-8 字节被当成 CP866」。ZIP 本身没问题：`ZipInfo.flag_bits & 0x800` 是 1，说明文件名带 UTF-8 标志，用正常的解压器（Python `zipfile`、`bsdtar`、UTF-8 locale 下的 `unzip`）都不会坏。

**是谁解压坏的**：很可能是 Wine 里的更新器/解压工具。文件时间也能对上——壁纸目录的 mtime 是 11 月 10 日 21:41，正好是 MAA 更新器尝试「自动修复缺失文件」的时间点；它把文件重新写了一遍，但名字按 CP866 落盘，于是越修越「缺」。目录里还留着 `MAA-v6.22.0-win-x64.zip.temp`，也是更新器的残留。

**修复**：不需要重下 282 MB，只要把名字还原。

```bash
python3 scripts/fix-maa-filenames.py            # 预览
python3 scripts/fix-maa-filenames.py --apply    # 重命名
```

脚本对每个路径分量做 `name.encode('cp866').decode('utf-8')`，能成功就改名；跳过 `config/`、`data/`、`debug/`、`cache/`、`platform-tools/`，避免碰用户数据。

这次实际重命名了 **316 个条目**（文件 + 目录），然后按 `filelist.txt` 校验：

```
filelist 条目: 10239，缺失: 0
```

重启 MAA，日志变成：

```
Integrity check passed, 9713 file(s) verified
```

弹窗消失。

**教训**：

- 「文件缺失」不等于「文件不存在」，也可能是「名字不匹配」；
- 工作目录决定 MAA 从哪里加载，但完整性检查是**逐文件比对**，两者不是一回事；
- 中文文件名跨 ZIP / Wine / 不同代码页时，先怀疑编码，不要急着重下几十 GB 的资源；
- 修完用 `filelist.txt` 做一次 `os.path.exists` 全量校验，比看弹窗可靠。
