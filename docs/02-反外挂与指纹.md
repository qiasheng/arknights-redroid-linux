# 02 · 反外挂与指纹：为什么游戏会「安静地消失」

这是整个项目里最值钱的一篇。如果只读一篇，读这篇。

## 1. 现象

环境已经能正常热更、能进登录页、甚至能进主界面。看起来一切正常，然后：

- 进主界面后 **10～60 秒**，游戏进程消失，回到桌面；
- 有时是点完「开始唤醒」后几秒，有时是刚看到基建；
- logcat **没有** `FATAL EXCEPTION`、**没有** `Abort message`、**没有** `signal 11`；
- `/data/tombstones` **没有**新增文件；
- `dmesg` 干净，没有 OOM，没有 lowmemorykiller；
- 事件日志里只有一条干巴巴的：

```
am_proc_died: [0,12345,com.hypergryph.arknights,default:com.hypergryph.arknights/10000,...]
```

或者 zygote 的两种说法之一：

```
Zygote: Process 12345 exited cleanly (0)
Zygote: Process 12345 exited due to signal 9 (Killed)
```

也就是说：**进程是被「正常结束」的，不是崩溃**。这一个细节决定了排查方向——不要再去翻 tombstone，也不要再怀疑段错误。

## 2. 先确认它不是 OOM / 系统回收

```bash
# 有没有被 ActivityManager 杀
adb -s 127.0.0.1:5556 logcat -d -b events | grep -E 'am_kill|am_proc_died|am_low_memory'

# 内核有没有 OOM
adb -s 127.0.0.1:5556 shell dmesg | grep -iE 'oom|killed process|lowmemory'

# 内存够不够
adb -s 127.0.0.1:5556 shell cat /proc/meminfo | head -5
```

如果 `am_kill` 没有、`dmesg` 没有、内存充足，那就不是系统杀的。系统杀会留下 `am_kill`，OOM 会留下内核日志。这里两者都没有。

## 3. 关键证据：属性超长

在 logcat 里搜 `libc`：

```bash
adb -s 127.0.0.1:5556 logcat -d -b all | grep -i 'has a value with length'
```

会看到（每次开机、每次有进程读这个属性时都会打）：

```
E/libc: The property "ro.build.fingerprint" has a value with length 102
        that is too large for __system_property_get()/__system_property_read();
        use __system_property_read_callback() instead.
```

Android 的属性值上限是 **92 字符**（`PROP_VALUE_MAX` = 92，含结尾 `\0` 的可用长度，所以最长只能放 91 个可见字符；达到 92 就会报这条）。

**后果**：任何用老接口 `__system_property_get()` 读 `ro.build.fingerprint` 的程序，读到的都是**空字符串**。

redroid 镜像原本派生出来的值是 102 字符：

```
redroid/redroid_x86_64/redroid_x86_64:11/RD2A.211001.002/eng.frank.20240527.144006:userdebug/test-keys
```

它并不是写死在 `/system/build.prop` 里的，而是 init 在启动时用 `ro.product.*` / `ro.build.*` 拼出来的（这就是为什么你在 build.prop 里搜不到它）。

## 4. 谁在定时检查：TenProtect

明日方舟国服内置腾讯 TenProtect 反外挂，在 logcat 里的痕迹：

```bash
adb -s 127.0.0.1:5556 logcat -d -b all | grep -iE 'tprt|com\.ace|GP7|gshell|TenProtect'
```

典型进程/线程名：

- `com.ace.gshell`（独立进程）
- `GP7Service` / `GP7Worker`（服务与工作线程）
- 游戏进程内的 `libtprt.so`

它启动后会周期性做设备环境校验。其中一项就是读 `ro.build.fingerprint`。读到空值 → 认为设备信息被抹掉 / 运行在篡改环境 → 结束游戏进程。

结束时它走的是「优雅退出」路径：从 Java 线程池调用 native，最终 `exit_group(0)`。所以 zygote 看到的是 `exited cleanly (0)`；某些路径下会先 `kill(getpid(), SIGKILL)`，于是变成 `signal 9 (Killed)`。两种表现都是同一个原因。

### 4.1 可选：怎么证明确实是「主动退出」

想自己复核的话，可以在宿主侧用 gdb 拦 `exit_group`。先放开 ptrace 限制：

```bash
sudo sysctl -w kernel.yama.ptrace_scope=0
```

拿 PID 并 attach（容器是独立 PID 命名空间，要 `nsenter`）：

```bash
CPID=$(sudo podman inspect -f '{{.State.Pid}}' redroid-arknights)
GPID=$(adb -s 127.0.0.1:5556 shell pidof com.hypergryph.arknights | tr -d '\r')
sudo nsenter -t "$CPID" -p -m gdb -p "$GPID" -batch \
  -ex 'catch syscall exit_group' \
  -ex 'continue' \
  -ex 'bt'
```

命中后回溯，会看到调用栈来自游戏内的 native 代码，而发起线程是 Java 侧的定时任务线程（我们当时看到的名字是 `pool-2-thread-1`）。用 `jdb` attach 到同一个进程看 Java 栈，能对上这个线程池。

> 这一步只用于「确认根因」，不是修复步骤。gdb attach 会让游戏卡住，看完记得 detach / 重启容器。

## 5. 修复：写一条合法的 90 字符指纹

redroid 的 `/system` 是**可写**的，且不需要 `adb remount`。直接用 `su 0` 改文件：

```bash
adb -s 127.0.0.1:5556 shell 'su 0 sh -c "
  cp -n /system/build.prop /system/build.prop.orig
  if grep -q \"^ro.build.fingerprint=\" /system/build.prop; then
    sed -i \"s|^ro.build.fingerprint=.*|ro.build.fingerprint=redroid/redroid_x86_64/redroid_x86_64:11/RD2A.211001.002/frank05271438:userdebug/test-keys|\" /system/build.prop
  else
    echo \"ro.build.fingerprint=redroid/redroid_x86_64/redroid_x86_64:11/RD2A.211001.002/frank05271438:userdebug/test-keys\" >> /system/build.prop
  fi
  sync
"'
```

这条指纹是 **90 字符**：

```
redroid/redroid_x86_64/redroid_x86_64:11/RD2A.211001.002/frank05271438:userdebug/test-keys
```

它复用了镜像里 `ro.system.build.fingerprint` 已经在用的那个值（`frank05271438`），格式合法、字段齐全，反外挂解析不会觉得奇怪。**不要随便截断到 91 字符以内**，`brand/product/device:release/id/incremental:type/tags` 的结构必须完整。

然后重启容器（不需要重建）：

```bash
sudo podman restart redroid-arknights
sleep 20
adb connect 127.0.0.1:5556
```

### 5.1 为什么「追加到 build.prop 末尾」能覆盖 init 拼出来的值

Android 的 `ro.*` 属性是「第一次设置生效」。init 的处理顺序是：

1. 先加载 `/system/build.prop`（以及 `/vendor`、`/odm` 等）；
2. 如果 `ro.build.fingerprint` 没有被任何 prop 文件显式设置，init 再用 `ro.product.*`、`ro.build.*` 拼一个出来。

所以只要 build.prop 里有一条显式的 `ro.build.fingerprint=`，init 就不会去拼那个 102 字符的值。文件里出现的位置不重要，**存在性**才重要。

> 这也解释了为什么在运行时 `setprop ro.build.fingerprint ...` 永远失败：`ro.*` 是只读的，只能在启动时由 prop 文件设置。

## 6. 验证

```bash
# 1) 长度必须是 90（只要 ≤ 91 且结构完整就行）
adb -s 127.0.0.1:5556 shell getprop ro.build.fingerprint | awk '{print length($0)}'
# 90

# 2) 内容对
adb -s 127.0.0.1:5556 shell getprop ro.build.fingerprint
# redroid/redroid_x86_64/redroid_x86_64:11/RD2A.211001.002/frank05271438:userdebug/test-keys

# 3) 文件里只有一条，且在最后
adb -s 127.0.0.1:5556 shell 'su 0 grep -n "^ro.build.fingerprint=" /system/build.prop'
# 63:ro.build.fingerprint=...

# 4) libc 的超长告警消失（重启后清空 logcat 再看）
adb -s 127.0.0.1:5556 logcat -c
adb -s 127.0.0.1:5556 logcat -d | grep -c 'has a value with length'
# 0
```

最直观的验证：进主界面后放 10 分钟，进程还在。

```bash
adb -s 127.0.0.1:5556 shell pidof com.hypergryph.arknights
```

## 7. 顺手检查：还有没有别的属性超长

镜像里可能不止一个。扫一遍所有属性：

```bash
adb -s 127.0.0.1:5556 shell getprop | awk -F': ' '
  {
    v = $0
    sub(/^[^:]*: \[/, "", v)
    sub(/\]$/, "", v)
    if (length(v) > 91) print length(v), $0
  }'
```

这次环境里只有 `ro.build.fingerprint` 一个。如果换镜像后出现别的，同样处理：在对应的 prop 文件里覆盖，重启。

## 8. 持久化：`restart` 保留，`rm` 不保留

- `podman restart redroid-arknights`：容器可写层还在 → 修改保留。
- `podman rm` + `podman run`：可写层销毁 → `/system/build.prop`、翻译层、`libvulkan.so.disabled` **全部回到镜像原样**，必须重跑 01 的第 6 节和本篇。

两种保命方式：

**A. 重建后跑脚本**（推荐，简单可复现）：

```bash
scripts/fix-fingerprint.sh 127.0.0.1:5556
```

**B. 把配置好的容器提交成新镜像**：

```bash
sudo podman commit redroid-arknights redroid-arknights:configured
# 以后用它创建新容器
sudo podman run ... docker.io/library/redroid-arknights:configured ...
```

> 注意 `podman commit` 会把 `/data` 之外的可写层一起打包，镜像会变大（几百 MB）。数据目录是 bind mount，不会进镜像。

## 9. 这一节踩过的误判

| 误判 | 为什么看起来像 | 实际 |
|---|---|---|
| 翻译层不兼容 | 确实有一次 `SIGABRT`，和 `libvulkan` 有关 | 那是启动崩溃，修完是另一个问题 |
| 内存不足被 OOM | 进主界面后死，很像资源加载爆内存 | `dmesg` 干净，无 `am_kill` |
| 网络断流导致掉线 | 有时刚好在下载/校验后发生 | 进程是被 `exit_group` 结束的，不是网络层 |
| MAA 把它杀了 | 用 MAA 启动后更容易观察到 | 不用 MAA、纯 `am start` 一样会死 |
| 游戏版本/热更坏了 | 重装 APK 后能多活一会儿 | 重装只是重置了计时起点 |
| 设备指纹「太假」 | 以为是模拟器检测 | 根因是「读出来是空」，不是「值不像真机」 |
